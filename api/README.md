# rvav API

`openapi.yaml` is the contract between the Go backend and the React frontend.
Both sides generate code from it, so change the spec first, then the code.

Current scope is **slice 1**: identity, projects and quota, catalog, request
forms with dynamic values, requests with their timeline and logs, deployments,
and live events. Approvals, day-2 actions and administration come in later
slices (see [roadmap](../docs/roadmap.md)).

## Working with the spec

```sh
# Lint (run from anywhere)
npx @redocly/cli@1 lint --config api/redocly.yaml api/openapi.yaml

# Go types and net/http server interface
go run github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@latest \
  -generate types,std-http-server -package api -o internal/api/api.gen.go api/openapi.yaml

# TypeScript types for the web client (used with openapi-fetch)
npx openapi-typescript@7 api/openapi.yaml -o web/src/lib/api/schema.d.ts
```

These commands will move into `make gen` and CI once the Go module and the web
app are set up. CI should fail when generated code is out of date.

## Conventions

### Base path and versioning
- Everything is under `/api/v1`.
- Within v1, changes are additive only: new endpoints, new optional fields,
  new enum values. Clients must ignore fields they don't know and handle
  unknown enum values gracefully (show them as plain text).

### Authentication
- `Authorization: Bearer <token>`, either an OIDC access token from the
  identity provider or an rvav API token (`rvav_pat_…`) for automation.
- Authorization is checked on every call. A resource the caller can't see
  returns `404`, not `403`, so IDs can't be probed.

### Identifiers
- IDs are opaque strings. Don't parse them.
- Some objects also have a human-friendly key that the API accepts wherever
  an ID is accepted: catalog items by `slug`, requests by `number`
  (`REQ-10491`).

### Names and formats
- JSON fields are `snake_case`.
- Timestamps are RFC 3339 in UTC (`2026-10-26T14:38:02Z`).
- Units are in the field name: `memory_mb`, `capacity_gb`,
  `typical_duration_seconds`.
- Nullable fields are sent as `null`, not omitted, when the absence means
  something (for example `lease.expires_at: null` means "never expires").

### Lists and pagination
- List endpoints return `{ "items": [...], "next_cursor": "..." }`.
- Pass `cursor=<next_cursor>` for the next page; `next_cursor` is `null` on
  the last page. `limit` defaults to 50, maximum 200.
- Filters with several values are comma-separated: `status=running,failed`.

### Errors
- Errors use RFC 9457 problem details (`application/problem+json`) and always
  include `request_id`, which is also in the `X-Request-Id` response header.
- Validation errors are `422` with an `errors` array. Each `field` is a JSON
  pointer into the submitted body (`/inputs/memory_gb`), so the form can put
  the message next to the right field.
- Messages are written for end users: they say what is wrong and how to fix it.

### Idempotency
- `POST /requests` requires an `Idempotency-Key` header (a UUID generated by
  the client per submit). Retrying with the same key returns the original
  response, so a double click or a network retry never creates two requests.

### Forms and dynamic values
- `GET /catalog/items/{id}/form` returns a JSON Schema for the inputs plus a
  UI schema (layout, widgets, value sources, dependencies, CEL rules).
- Fields with a `value_source` are resolved by `POST /forms/values`. The
  browser never calls vCenter, EfficientIP or AWX directly.
- `POST /requests/preview` validates a draft and returns names, quota impact,
  the approval path, placement and lease. The form calls it (debounced) to
  keep the summary panel current.
- The server re-validates everything on submit; client-side checks are only
  for speed.

### Long-running work
- `POST /requests` returns `202` immediately. Progress is in
  `GET /requests/{id}/steps` (a tree: AWX jobs have one child per task) and
  `GET /requests/{id}/steps/{stepId}/log` (read incrementally by offset).

### Live events
- `GET /events?topics=…` is a Server-Sent Events stream. The web app opens
  one per tab and applies events to its TanStack Query cache.
- Each event carries an `id`. After a reconnect, the client sends
  `Last-Event-ID`; if the gap is too old, the server sends `resync` and the
  client refetches.
- The server sends `heartbeat` every 15 seconds so proxies keep the
  connection open.
- `request.log` only signals that new lines exist; the client fetches them
  with `getStepLog`. This keeps the stream small when an AWX job is verbose.

### Secrets
- Form fields marked `secret` are stored encrypted, passed to AWX as
  `extra_vars` at launch only, and returned by the API as `"••••"`.
