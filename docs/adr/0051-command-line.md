# ADR-0051: rvavctl, a command line for users

- Status: accepted
- Date: 2026-11-19
- Builds on the API contract of [ADR-0006](0006-contract-first-vertical-slices.md)
  and the sign-in of [ADR-0010](0010-identity-provider.md) and
  [ADR-0030](0030-settings-and-local-administrator.md). O1.1 (#167).

## Context
vRA has a command line and SDKs: requesters script requests, owners run
day-2 actions from a shell, approvers decide from a terminal. rvav had its
API, its contract (`api/openapi.yaml`) and API tokens, but every script
wrote its own calls. O1.2 (#168) adds a Terraform provider and a
PowerShell module, which need the same pieces: a client of the API, a
way to sign in, and somewhere to keep the sign-in.

## Decision

### A generated client, public
`pkg/rvavclient` is generated by oapi-codegen from the contract, as the
server's `internal/api` is (`make gen`, `make gen-check`): models and a
client with typed responses. It lives under `pkg/` so that O1.2's
provider, and tools outside this repository, can import it. Next to the
generated code it has what every client needs:
- `Connect(server, tokens)`: the API's address from rvav's
  (`https://rvav.corp.example` or `…/api/v1`), and the bearer token from
  an `oauth2.TokenSource` on every call, refreshed when it expires.
- `Check(resp, body)`: a non-2xx answer as an `*Error` holding the
  problem details (RFC 9457), whose message lists each field error by its
  input's name (`role`, not `/inputs/role`).
- `Profiles`: named rvavs and their credentials, in one JSON file only
  its user may read (`0600` in a `0700` directory), replaced at once so
  that a reader never sees half of it. A refreshed token is written back
  into the file as it is then, so that two rvavctl processes don't lose
  each other's profiles.

### How rvavctl signs in
`rvavctl login --server URL` reads `GET /auth/options`, as the web app
does, and signs in at the provider it names, with the web app's client
(`--client-id` for another one):
- **In the browser:** the authorization code flow with PKCE, the browser
  coming back to a loopback address (`http://127.0.0.1:<port>/callback`,
  RFC 8252). The port is any free one, or `--callback-port` for a
  provider that registers exact ports.
- **On another device** (`--device`): the device authorization grant
  (RFC 8628), for SSH sessions.
- **`offline_access`** is asked for when the provider supports it, so
  that the sign-in outlives the provider's browser session (Entra ID
  gives no refresh token without it).

The access token is the web app's: same client, same audience, same
groups, so rvav checks it as it checks the browser's, and the user has
the roles their groups give, approvals included. No change to the API's
authentication was needed. The client's ID goes in the token request's
body (a public client has no secret).

The other ways in:
- **An API token** (`--with-token`, read on standard input so that it
  stays out of the shell's history). It acts with the roles given to the
  user in rvav itself, not those from their groups, as the API decided for
  automation.
- **`RVAV_URL` and `RVAV_TOKEN`** in the environment, for scripts and CI,
  without a file. They are the names AWX already gives the jobs rvav
  launches. `RVAV_TOKEN` wins over a profile.
- **Development mode:** an rvav without a provider that signs everyone in
  as one user; the profile then keeps only the address.

A profile's credentials go to its own rvav only: `--server` naming
another sends none.

### The commands
They follow the web app's pages and use its words:
- `login`, `logout`, `whoami`;
- `catalog list | show | choices | request`;
- `requests list | show | wait | cancel | retry`;
- `deployments list | show | actions | run`;
- `approvals list | show | approve | reject`.

`cobra` parses them: subcommands, help, and shell completion
(`rvavctl completion`). It is the one new dependency.

**Inputs** are given with `--input name=value`, typed by the form's JSON
Schema (`4` is a number for an integer, `a,b` a list for an array, JSON
for an object), or with a JSON or YAML file (`--inputs`). As in the web
app, they go on top of the form's initial values; rvav checks the rest.
Since [ADR-0055](0055-inputs-left-out.md) the server fills in the initial
values, and rvavctl sends only the inputs given.
`catalog choices` lists what a value source offers for an input, given
the environment and the other inputs. `--dry-run` previews a request with
its validations and fails when rvav would refuse it. A day-2 action that
deletes or can't be undone needs `--yes`.

**Output:** a table, or with `-o json` what the API returns, its fields
and their order kept; a list is a JSON array of its items, all its pages
read up to `--limit`. Data goes to standard output, progress and errors to
standard error. `--wait` reads the request every two seconds until it
ends, and exits with 1 unless it succeeded.

Every create sends a new `Idempotency-Key`.

### Release
`make cli-dist` builds rvavctl for Linux, macOS and Windows on amd64 and
arm64, with the release's version, into `dist/rvavctl/` as archives with a
`SHA256SUMS` file, to attach to the release. `make build` puts it in
`bin/`.

## Consequences
- The contract is the client's: an API change regenerates both sides, and
  `make gen-check` fails when the client is out of date.
- The generated client is large (about 2.5 MB of Go, about 3.5 MB per
  archive), and it is the price of a typed client of every operation for
  O1.2.
- The identity provider must accept the loopback redirect, and the device
  grant for `--device`, on rvav's client
  ([administrator guide](../guides/admin.md#signing-in-with-rvavctl)).
  The development realm does both.
- The sign-in sits in a file, readable by its user only, as kubectl's and
  the cloud CLIs' do. `logout` forgets it; a refresh token stays valid at
  the provider until it expires.
- An API token can't approve as a member of an approver group, as before:
  approvers sign in with `rvavctl login`.
